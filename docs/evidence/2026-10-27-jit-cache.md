# LuaJIT cache investigation, 2026-10-27

All three runs below used clean `a00a1b8`, the owned Ubuntu 24.04 container
(two CPUs, 4 GiB), GTK/WGPU, Xvfb and Mesa llvmpipe. No Kiwi build or test ran
concurrently. Shared workstation load and thermals were uncontrolled. These
are diagnostic experiments, not a three-trial relative performance baseline.
The workload used saturated styled Unicode, full-screen history, 10,000 retained
rows, six warmup inputs, twenty measured inputs and a requested 60-second soak.
The ordinary service used 4 KiB chunks, a 16 KiB byte ceiling and an 8 ms elapsed
target checked after each parse. The response ceiling remained two seconds.

| Experiment | Measured inputs | Code-cache flushes | Machine-code allocation aborts | Result |
| --- | ---: | ---: | ---: | --- |
| [Default cache, trace counters](2026-10-27-jit-default-gtk.json) | 0/20 | 55 | 55 | Failed during warmup |
| [4 MiB cache, trace counters](2026-10-27-jit-4m-gtk.json) | 20/20 | 0 | 0 | Passed absolute response and memory gates |
| [4 MiB cache, no trace counters](2026-10-27-jit-4m-without-counters-gtk.json) | 0/20 | Not measured | Not measured | Failed during warmup |

The [default log](2026-10-27-jit-default-gtk.log) reports 20,194 recording starts
and 13,252 completed traces, repeatedly invalidated by flushes. The
[4 MiB log](2026-10-27-jit-4m-gtk.log) reports 2,636 starts and 799 completed traces,
with a maximum trace number of 789. This supports a bounded cache increase to
avoid recompilation churn on older LuaJIT builds. It does not justify raising
the separate trace-count limit or relaxing the response gate.

The container uses LuaJIT 2.1.1703358377. The corresponding upstream snapshot
[defaults to 512 KiB](https://github.com/LuaJIT/LuaJIT/blob/c525bcb9024510cad9e170e12b6209aedb330f83/src/lj_jit.h).
[Exceeding this configured ceiling raises MCODEAL](https://github.com/LuaJIT/LuaJIT/blob/c525bcb9024510cad9e170e12b6209aedb330f83/src/lj_mcode.c),
whose [error handler flushes all traces](https://github.com/LuaJIT/LuaJIT/blob/c525bcb9024510cad9e170e12b6209aedb330f83/src/lj_trace.c).
The error label therefore does not by itself establish operating-system memory
exhaustion. Increasing only `maxmcode` eliminated it in this diagnostic run.

The successful run lasted 72.59 seconds after warmup, retained exactly 10,000
rows and evicted 93,676. RSS quarter-median growth was 480 KiB, Lua heap growth
was negative and peak RSS was 654,264 KiB. Input p95 was still 1,744.80 ms and
maximum 1,996.15 ms: barely inside the gate, not acceptable interactive latency.
The slowest input reached the PTY after 3.72 ms, then spent 750.72 ms parsing,
387.01 ms preparing models and 793.17 ms rendering across four turns.

The run without trace callbacks took 28.92 seconds to show the first ready frame
and failed at warmup sequence 2, after 2,429.94 ms. Input-to-PTY time was
134.90 ms. Its delayed interval included substantial parser, model preparation,
rendering and event-wait work. There is no evidence here that the cache setting
alone fixes sustained responsiveness, nor that all failures share one cause.

## Reproduction and instrumentation

The clean source revision predates `kiwi.runtime`. The default run used a shell
wrapper executing `luajit /tmp/kiwi-jitstats.lua "$@"`; the 4 MiB run executed
`luajit -Omaxmcode=4096 /tmp/kiwi-jitstats.lua "$@"`. The third wrapper executed
`luajit -Omaxmcode=4096 "$@"` directly. These external wrappers are not captured
by the reports' Git cleanliness or old runtime metadata. Do not compare them
as if their runtime settings were identical. The trace callback counts events
and abort reason labels using `jit.vmdef.traceerr`, then detaches before exit:

```lua
local counts = { start = 0, stop = 0, abort = 0, flush = 0,
  maximum_trace = 0, abort_reasons = {} }
local vmdef = require("jit.vmdef")
local function event(what, tr, func, pc, reason)
  if counts[what] ~= nil then counts[what] = counts[what] + 1 end
  if type(tr) == "number" then counts.maximum_trace = math.max(counts.maximum_trace, tr) end
  if what == "abort" then
    local label = type(reason) == "number" and (vmdef.traceerr[reason] or tostring(reason)) or tostring(reason)
    counts.abort_reasons[label] = (counts.abort_reasons[label] or 0) + 1
  end
end
jit.attach(event, "trace")
local filename = table.remove(arg, 1)
local ok, message = xpcall(assert(loadfile(filename)), debug.traceback)
jit.attach(event)
io.stderr:write("KIWI_JIT_STATS ", require("kiwi.bench.json").encode(counts), "\n")
assert(ok, message)
```

Counter callbacks can perturb trace recording and timings. All runs additionally
used the fixture's pending-input phase timers. CPU times are process-wide and
include native worker threads. Longer native qualification remains open.

## Production setting and ordinary output service

Commit `c1484cf` applies the finite 4 MiB setting at app startup and to benchmarks
and the deterministic test runner. `make check` passed 677 Lua tests in 132
suites, 19 PTY tests and its associated checks. Linux core qualification passed
436 tests in 74 suites. CLI checks verify that initialization preserves both
explicitly enabled and explicitly disabled execution modes and optimization flags.

Real-PTY burst checks at clean `c1484cf` used the shared cooperative output service
and unchanged 250 ms maximum-turn / 64 MiB retained-heap gates. They ran
sequentially, without other Kiwi builds or tests, on the shared workstation:

- [Linux](2026-10-27-cooperative-burst-linux.log): printable 1 MiB passed
  (28.91 ms maximum turn); mixed ANSI failed at 255.06 ms. Later cases were
  not reached.
- [Intel macOS](2026-10-27-cooperative-burst-macos.log): printable 1 MiB,
  mixed ANSI, Unicode and query-response cases passed (maximum turns 124.29,
  174.36, 44.35 and 31.30 ms respectively). The query received its six-byte
  terminal reply. The 10 MiB case failed at 817.36 ms.

These failures occurred after child shutdown. This version of the burst harness
asserts before writing JSON, so the captured stdout/stderr logs are the retained
evidence. Neither is a complete burst qualification. There was no timeout or
threshold increase to produce a pass.

Inspection also found one avoidable allocation per printed character in REP
bookkeeping. An isolated 20,000-character overwrite probe at `c1484cf` allocated
2,187.5 KiB with garbage collection stopped. Storing the last glyph and codepoint
directly in the state reduced this to 0.0 KiB with JIT enabled and 0.6 KiB with it
disabled on Intel macOS. The probe repeatedly writes `A` at column zero after
2,000 warmup writes, excluding scrolling and cell creation. The new regression
test allows 128 KiB and fails against the old `state.lua` (2,187.59 KiB measured).
Unicode repetition, resets, alignment output and staged configuration isolation
are checked separately. This removes known allocation churn; it does not by
itself establish a native latency or burst-test improvement.

After the allocation change (`5e20aeb`) and child-watcher fixture correction
(`e568a15`), `make check` passed 680 Lua tests in 132 suites, 19 PTY tests and
all associated checks on Intel macOS. The earlier attempt passed the Lua/PTy
tests but failed the child-watcher fixture's assumption that Darwin process-filter
`ESRCH` implies immediate `waitpid(WNOHANG)` success. The fixture now retries
within its existing 1.5-second observation budget and separately exercises a
child that is initially unreapable; the production timed fallback is unchanged.
Linux core validation passed 439 tests in 74 suites and the child-watcher fixture.
At clean `e568a15`, all [11 local application workflows](2026-10-27-repeat-allocation-applications.json)
and [six loopback SSH workflows](2026-10-27-repeat-allocation-ssh.json) passed.
These are PTY/parser/workflow checks, not native desktop or latency qualifications.

## Native follow-up with both production changes

At clean `4ca2add`, the [GTK 60-second history run](2026-10-27-history-linux-gtk-no-repeat-allocation.json)
completed all 20 measured inputs without the external LuaJIT wrapper or trace
callbacks. The fixture's normal pending-input phase timers remained enabled.
Input p95 was 501.98 ms and maximum 543.74 ms. The observed post-warmup duration
was 66.70 seconds, with exactly 10,000 retained rows and 106,201 evictions.

This run still **failed**: RSS quarter-median growth was 70,860 KiB (69.2 MiB),
above the unchanged 64 MiB gate. Lua heap growth was 6,149.49 KiB, below its
16 MiB gate; sampled peak RSS was 654,436 KiB. The first resource sample retained
only 6,700 rows, so the observation window includes capacity filling. This does
not establish a leak, but it also does not qualify steady-state memory. First
ready presentation took 8.94 seconds. Shared host conditions prevent treating
this single run as a controlled speed comparison. A longer completed soak is
still required; neither memory nor response thresholds were relaxed.

The subsequent [requested 600-second run](2026-10-27-history-linux-gtk-runtime-warmup-failure.json)
at clean `9192e9a` failed during warmup sequence 6, before collecting any measured
inputs. History had reached 10,000 rows and evicted 3,504. The delayed input
reached the PTY after 3.63 ms, but its acknowledgment took 2,400.23 ms. Across four
4 KiB reads, parsing used 805.15 ms wall time and model preparation 1,343.71 ms;
rendering used 136.90 ms. Parse/preparation CPU and wall times were nearly equal.
First ready presentation took 2.12 seconds. No steady-state memory conclusion
can be drawn from this interrupted warmup. The successful shorter response
series therefore does not establish reliable sustained responsiveness.
