# LuaJIT cache investigation, 2026-10-27

All three runs below used clean `a00a1b8`, the owned Ubuntu 24.04 container
(two CPUs, 4 GiB), GTK/WGPU, Xvfb and Mesa llvmpipe. No Kiwi build or test ran
concurrently. Shared workstation load and thermals were uncontrolled. These
are diagnostic experiments, not a three-trial relative performance baseline.
The workload used saturated styled Unicode, full-screen history, 10,000 retained
rows, six warmup inputs, twenty measured inputs and a requested 60-second soak.
The ordinary service used 4 KiB chunks, a 16 KiB byte ceiling and an 8 ms elapsed
target checked after each parse. The response ceiling remained two seconds.

| Experiment | Measured inputs | Code-cache flushes | Machine-code allocation aborts | Result |
| --- | ---: | ---: | ---: | --- |
| [Default cache, trace counters](2026-10-27-jit-default-gtk.json) | 0/20 | 55 | 55 | Failed during warmup |
| [4 MiB cache, trace counters](2026-10-27-jit-4m-gtk.json) | 20/20 | 0 | 0 | Passed absolute response and memory gates |
| [4 MiB cache, no trace counters](2026-10-27-jit-4m-without-counters-gtk.json) | 0/20 | Not measured | Not measured | Failed during warmup |

The [default log](2026-10-27-jit-default-gtk.log) reports 20,194 recording starts
and 13,252 completed traces, repeatedly invalidated by flushes. The
[4 MiB log](2026-10-27-jit-4m-gtk.log) reports 2,636 starts and 799 completed traces,
with a maximum trace number of 789. This supports a bounded cache increase to
avoid recompilation churn on older LuaJIT builds. It does not justify raising
the separate trace-count limit or relaxing the response gate.

The container uses LuaJIT 2.1.1703358377. The corresponding upstream snapshot
[defaults to 512 KiB](https://github.com/LuaJIT/LuaJIT/blob/c525bcb9024510cad9e170e12b6209aedb330f83/src/lj_jit.h).
[Exceeding this configured ceiling raises MCODEAL](https://github.com/LuaJIT/LuaJIT/blob/c525bcb9024510cad9e170e12b6209aedb330f83/src/lj_mcode.c),
whose [error handler flushes all traces](https://github.com/LuaJIT/LuaJIT/blob/c525bcb9024510cad9e170e12b6209aedb330f83/src/lj_trace.c).
The error label therefore does not by itself establish operating-system memory
exhaustion. Increasing only `maxmcode` eliminated it in this diagnostic run.

The successful run lasted 72.59 seconds after warmup, retained exactly 10,000
rows and evicted 93,676. RSS quarter-median growth was 480 KiB, Lua heap growth
was negative and peak RSS was 654,264 KiB. Input p95 was still 1,744.80 ms and
maximum 1,996.15 ms: barely inside the gate, not acceptable interactive latency.
The slowest input reached the PTY after 3.72 ms, then spent 750.72 ms parsing,
387.01 ms preparing models and 793.17 ms rendering across four turns.

The run without trace callbacks took 28.92 seconds to show the first ready frame
and failed at warmup sequence 2, after 2,429.94 ms. Input-to-PTY time was
134.90 ms. Its delayed interval included substantial parser, model preparation,
rendering and event-wait work. There is no evidence here that the cache setting
alone fixes sustained responsiveness, nor that all failures share one cause.

## Reproduction and instrumentation

The clean source revision predates `kiwi.runtime`. The default run used a shell
wrapper executing `luajit /tmp/kiwi-jitstats.lua "$@"`; the 4 MiB run executed
`luajit -Omaxmcode=4096 /tmp/kiwi-jitstats.lua "$@"`. The third wrapper executed
`luajit -Omaxmcode=4096 "$@"` directly. These external wrappers are not captured
by the reports' Git cleanliness or old runtime metadata. Do not compare them
as if their runtime settings were identical. The trace callback counts events
and abort reason labels using `jit.vmdef.traceerr`, then detaches before exit:

```lua
local counts = { start = 0, stop = 0, abort = 0, flush = 0,
  maximum_trace = 0, abort_reasons = {} }
local vmdef = require("jit.vmdef")
local function event(what, tr, func, pc, reason)
  if counts[what] ~= nil then counts[what] = counts[what] + 1 end
  if type(tr) == "number" then counts.maximum_trace = math.max(counts.maximum_trace, tr) end
  if what == "abort" then
    local label = type(reason) == "number" and (vmdef.traceerr[reason] or tostring(reason)) or tostring(reason)
    counts.abort_reasons[label] = (counts.abort_reasons[label] or 0) + 1
  end
end
jit.attach(event, "trace")
local filename = table.remove(arg, 1)
local ok, message = xpcall(assert(loadfile(filename)), debug.traceback)
jit.attach(event)
io.stderr:write("KIWI_JIT_STATS ", require("kiwi.bench.json").encode(counts), "\n")
assert(ok, message)
```

Counter callbacks can perturb trace recording and timings. All runs additionally
used the fixture's pending-input phase timers. CPU times are process-wide and
include native worker threads. Longer native qualification remains open.
